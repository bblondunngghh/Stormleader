[FINDING 1] /dashboard — "Days in Stage" panel measures the wrong thing
STATUS: CONFIRMED DEFECT — NOT FIXED (fix requires a schema change; out of charter)
Severity: medium (silent wrong data, no error signal)

SYMPTOM: panel shows avg 0.0 days for all 5 stages and "stuck_leads": 0,
while 22 leads have sat in stage 'new' for an average of 90 days
(created_at spans 80-140 days ago).

EVIDENCE:
  GET /api/crm/dashboard/days-in-stage -> avg_days:0 for all 5 stages
  DB: all 31 leads updated_at = 2026-08-11 05:01:43..05:10:49
      all 31 leads created_at  = 80..140 days ago
      avg_days_by_updated_at = 0.01 ; avg_days_by_created_at = 90.18 (stage 'new')

ROOT CAUSE (crm.js:849):
  ROUND(AVG(EXTRACT(EPOCH FROM (NOW() - updated_at)) / 86400), 1) as avg_days
  stuck_leads = COUNT(*) FILTER (WHERE updated_at < NOW() - INTERVAL '7 days')
  `updated_at` is a generic row-modification timestamp, NOT a stage-entry
  timestamp. Postgres trigger `trg_leads_updated` (EXECUTE FUNCTION
  update_updated_at()) fires on EVERY UPDATE of leads. So adding a note,
  assigning a rep, or re-scoring a lead resets its "days in stage" to 0
  and clears its "stuck" flag. The panel's entire purpose (find leads
  rotting in a stage) is defeated by any unrelated edit.

WHY THIS RUN SAW 0.0 EVERYWHERE: leadScoringService.scoreAllLeads() re-scores
  every lead whose score is >24h old (LIMIT 100) and its UPDATE trips the
  trigger. It is route-triggered (crm.js:298), not scheduled - the prior QA
  stage's write sweep hit it, zeroing all 31 rows. NOT a recurring job, so
  the panel is not PERMANENTLY zero, but it is wrong after any lead edit.

WHY NOT FIXED HERE: there is no stage-entry timestamp anywhere in the schema.
  leads has only: created_at, updated_at, last_contact_at, deleted_at,
  lead_score_updated_at. The `activities` table records only 'note' and 'call'
  types - no stage-change rows. The information required to compute this
  correctly IS NOT RECORDED. A correct fix = new column `stage_changed_at`
  + backfill + write it on every stage transition = schema migration and
  new feature work, which the QA charter excludes.
RECOMMEND: ticket for the developer.
