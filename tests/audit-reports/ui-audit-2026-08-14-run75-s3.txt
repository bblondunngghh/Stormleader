HEADLINE
--------
1 defect found and fixed. The app is in genuinely good shape on icons, buttons,
sidebar and form components — those audits came back clean against real
measurement, not assumption. The one real defect was invisible to every
rendering check: a CSS class referenced by 4 components that does not exist.

*** THE LESSON FOR THE NEXT STAGE ***
A class that is declared but undefined renders IDENTICALLY to one that works,
as long as something else happens to supply the same styling. `modal-scale-in`
animated correctly in all 4 components, so every screenshot, every computed-
style sweep and every visual diff would have passed it. It was only findable by
diffing the set of classNames USED in JSX against the set of selectors DEFINED
in CSS. That diff is a one-command check and it should be standing:
  grep -o 'className="[^"]*"' -r src/ | extract tokens | comm -23 with CSS selectors
This is the same shape as Run 75-s2's winning check (grep enum consumers, diff
against files defining a label map, the odd one out is the bug). Both find bugs
by comparing two sets that SHOULD be equal, rather than by looking at output.

AUDIT 3 — TOOLBAR / HEADER CONSISTENCY : NO SHARED HEADER COMPONENT
================================================================================
17 of 18 routes have NO .page-header / <header> / .view-header element.
There is no shared page-header component or class in the app; each view builds
its own top row inline. Consequences measured:

  - Page heading sizes: 28px/820 (Dashboard), 24.5px/700 (Calendar),
    22px/700 (Storm Archive), 22px/800 (Materials, Subcontractors),
    20px/800 (Work Orders) = 5 treatments.
  - THERE IS NO <h1> ANYWHERE IN THE APP. Every page's top heading is an <h2>,
    and /reports has no page-level heading at all — its first heading is an
    <h3> chart title ("Revenue") 247px down the page.
  - .main-content padding is 0px on 16 routes and 24px on 2 (/storm-catalog,
    /reports), so each view owns its own outer padding.

This is a structural/architectural gap, not a rendering bug — every page looks
deliberate on its own. Introducing a shared PageHeader component would be a
refactor across 18 views, which is explicitly outside this charter. Recorded
as a developer ticket. The missing <h1> is the part with real accessibility
weight and is the cheapest to fix later.

AUDIT 6 — SPACING & ALIGNMENT : known two-system issue CONFIRMED STILL PRESENT
================================================================================
Root font-size is 14px, and Tailwind rem utilities resolve against it, so any
rem-based spacing lands on fractional pixels. Measured .glass content padding:
  /dashboard  17.5px, 8.75px 21px, 10.5px 17.5px   <- rem on a 14px root
  /pipeline   14px, 10.5px 14px, 8.75px 14px       <- rem on a 14px root
  /estimates  24px, 16px 24px                      <- px vars
  /invoices   24px, 16px 24px, 12px 24px           <- px vars
  /expenses   24px, 16px 24px                      <- px vars
  /reports    20px                                 <- px vars
  /leads      12px 24px                            <- px vars
Five distinct .glass paddings from two coexisting spacing systems. This is
exactly the root cause Run 74 identified and it is unchanged. Every fractional
pixel in the app traces back to it. Unifying it means converting Dashboard and
Pipeline off Tailwind rem spacing — a large refactor, outside this charter.
Grid gaps are otherwise consistent: 12px on every stats-grid and dashboard
grid; /reports' reports-grid uses 20px to match its own 20px card padding.

AUDIT 7 — MODAL CONSISTENCY : 1 DEFECT FOUND AND FIXED
================================================================================
22 `.modal-backdrop` usages inventoried across 15 components; the direct child
of each was resolved statically and the pattern verified in-browser.

19 of 22 wrap their panel: .modal-backdrop > .glass — these get
`modal-backdrop-in` on the backdrop and `modal-scale-in` on the panel from
index.css:4467-4474. Confirmed live on the Add Expense modal: backdrop
animation modal-backdrop-in, panel animation modal-scale-in, horizontally
centered, on-screen, radius 20px, exactly 1 close button.

*** THE DEFECT (FIXED, f788c22) ***
Four components render their panel as className="glass modal-scale-in":
  CalendarView.jsx:260, DripSequences.jsx:585,
  EstimatesView.jsx:2872, InvoicesView.jsx:1059
`.modal-scale-in` WAS NEVER DEFINED AS A CSS SELECTOR. Grepping index.css for
`.modal-scale-in` returns nothing; `modal-scale-in` existed ONLY as a
@keyframes name (index.css:4282) and inside three `animation:` shorthands.
The class computed to animation-name: none.

Those four modals still animated — but only by accident, because each also
matches the SEPARATE `.modal-backdrop > .glass` rule. The declared contract was
silently unenforced. Any of them restructured to the sibling-backdrop pattern
(already used by PhotoAnnotator and LeadDetail) would have silently lost its
animation with no visible cause and nothing to grep for.

FIX: defined `.modal-scale-in` with the identical 200ms var(--ease-apple) both
timing the .glass rule already applied, so all four existing usages are
behaviourally unchanged.
VERIFIED: `.modal-scale-in` now computes animation-name modal-scale-in / 0.2s /
both (previously `none`). `.modal-backdrop` -> modal-backdrop-in and
`.modal-backdrop > .glass` -> modal-scale-in both still resolve unchanged, so
no regression to the 19 working modals. Add Expense modal re-opened and
re-measured after the change: still centered, on-screen, both animations firing.
vite build passes.

--- Deliberate skips (fix attempted or considered, then rejected on evidence) ---
TWO modal surfaces use a SIBLING-backdrop pattern — a self-closing
<div className="modal-backdrop" /> followed by a sibling panel — which
structurally cannot match `.modal-backdrop > .glass`. They are the only two
overlays in the app that open with NO entrance animation:

  1. LeadDetail.jsx:2474 (Weather Damage Verification Report).
     I APPLIED the new class here, then REVERTED it. The panel is centered with
     transform: translate(-50%, -50%), and the modal-scale-in keyframe ends at
     `transform: none` — which would have CLOBBERED the centering and thrown the
     modal off-centre. Reverting was correct. Animating this panel requires
     changing how it is centred first, which is a refactor, not a QA fix.
     >>> Do not naively apply modal-scale-in to a transform-positioned element. <<<

  2. PhotoAnnotator.jsx:208. Safe on positioning (inset-based, no existing
     transform) and safe on caching (getPos reads
     canvasRef.getBoundingClientRect() live per pointer event at :87, nothing is
     cached at mount). BUT getPos does NOT normalise by canvas.width/rect.width
     — it only subtracts the rect origin — so a 200ms scale animation would
     create a brief window where drawing coordinates are skewed. That is a new
     failure mode introduced into a working feature for a cosmetic gain.
     Left alone per the charter.

Both are recorded as developer tickets. Neither is a regression; both predate
this run.

--- Modal properties re-confirmed as intentional, do NOT normalise ---
  - z-index spread (200/300/400/1000/9999/99998) is functional stacking order
    for nested overlays.
  - Backdrop variance (0.5+blur4 / 0.6+blur8 / 0.6+none / 0.75+blur4) is
    per-context.
  - .slide-over is a second legitimate overlay pattern; a missing
    .modal-backdrop there is correct.
  - Modal title sizes (3 variants) + the ExpensesView.jsx:105 <h3> heading-level
    skip re-confirmed present. Known, deliberately not half-converted.
  - Esc-to-close remains inconsistent (1 of 5). Unchanged, still deferred.
