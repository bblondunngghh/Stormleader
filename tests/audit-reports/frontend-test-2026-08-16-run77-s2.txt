== DEFECT 1 (FIXED) — dashboard team leaderboard filtered nothing ==
Dashboard.jsx:1836 navigates to `/leads?assigned_rep=${rep.id}`.
LeadList.jsx:119-128 reads search|stage|priority|source|min_score|sort_by|sort_dir|
page|limit from searchParams — it never read assigned_rep. Worse, the URL-sync
effect (LeadList.jsx:190-201) rewrites the query string from its own state, so the
param was STRIPPED FROM THE ADDRESS BAR immediately after arrival.
Measured before: click a rep -> /leads, "Showing 1-24 of 24 leads" (unfiltered).
The server has always supported this filter but under a DIFFERENT NAME:
crm.js:23 destructures `assigned_rep_id`, not `assigned_rep`.
Fix: LeadList reads `assigned_rep`, sends it as `assigned_rep_id`, preserves it in
the URL, and surfaces it through the EXISTING filter-pill + Clear All pattern.
Measured after: /leads?assigned_rep=45cc729d..., request carries
assigned_rep_id=45cc729d..., "Showing 1-1 of 1 leads", rep column = "Miles M",
pill reads "Rep: Miles Martin"; removing the pill restores 24 rows and a clean URL.

== TESTER-ERROR TRAP THAT COST ~8 TURNS (NEW, HIGH VALUE) ==
Mid-session the Playwright input pipeline DIED SILENTLY. Symptoms that look exactly
like a catastrophic app bug: every Settings tab "ignored" real clicks while
element.click() worked; sidebar nav clicks did nothing; keyboard.press produced no
keydown. Playwright reported the clicks as OK (no timeout) and elementFromPoint
returned the correct button.
THE TELL: page.mouse.move() over an element produced NO :hover match, and ZERO
events reached a document-level CAPTURE listener. Synthesized input was not being
delivered to the renderer at all.
FIX: browser_close, then re-navigate — the session and login survive.
=> RUN THIS HEALTH CHECK BEFORE TRUSTING ANY "the app ignored my click" RESULT:
   mouse.move onto a known element, then assert document.querySelectorAll(':hover').length > 0.
Without it this run would have filed "no button in the app responds to clicks".
