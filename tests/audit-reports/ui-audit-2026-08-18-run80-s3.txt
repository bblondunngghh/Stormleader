================================================================================
THE DEFECT — calendar priority badge could never show a colour
================================================================================
CalendarView.jsx:140 renders:

    className={`calendar-event-content__priority
                calendar-event-content__priority--${priority}`}

`priority` originates at crm.js:1056 (`SELECT t.priority FROM tasks t`).
`tasks.priority` is column type `lead_priority` — an ENUM whose only members are
`hot | warm | cold` (006_leads.sql:2). Confirmed against the LIVE DB:

    tasks.priority udt_name -> lead_priority
    pg_enum labels          -> hot, warm, cold
    live distribution       -> warm x2, NULL x2

index.css defined modifiers for a completely different vocabulary:

    .calendar-event-content__priority--urgent   (defined, UNREACHABLE)
    .calendar-event-content__priority--high     (defined, UNREACHABLE)
    .calendar-event-content__priority--medium   (defined, UNREACHABLE)
    .calendar-event-content__priority--low      (defined, UNREACHABLE)
    --hot / --warm / --cold                      (REACHABLE, NOT DEFINED)

The set difference is total: zero of the three values that can ever flow in had
a rule, and zero of the four defined rules could ever match. The base class
supplies font-size/weight/padding/radius but NO background and NO color, so the
badge rendered transparent with inherited text colour on every calendar event —
a colour-coded priority indicator structurally incapable of showing a colour.

PROOF (before) — DOM-injection probe, zero DB writes:
    hot     -> background rgba(0, 0, 0, 0)   color oklch(0.95 0.005 260)  [inherited]
    warm    -> background rgba(0, 0, 0, 0)   color oklch(0.95 0.005 260)  [inherited]
    cold    -> background rgba(0, 0, 0, 0)   color oklch(0.95 0.005 260)  [inherited]
    urgent  -> background oklch(0.55 0.2 25 / 0.3)    color oklch(0.8 0.18 25)
    high    -> background oklch(0.55 0.15 70 / 0.3)   color oklch(0.8 0.15 70)
    medium  -> background oklch(0.55 0.12 220 / 0.3)  color oklch(0.8 0.12 220)
    low     -> background oklch(0.4 0.05 260 / 0.3)   color oklch(0.7 0.03 260)

FIX: renamed the modifiers to the real enum values on the same red/amber/blue
hues the app already uses for priority at .lead-table__priority-dot--hot/warm/
cold (index.css:1916-1918), preserving the badge's existing translucent-
background + solid-text formula. CSS only — no JSX, server or schema change.

PROOF (after) — a REAL rendered calendar event, not an injected probe. One
existing task's due_date was temporarily set, the badge measured, then the
due_date reverted to NULL (tasks with_due back to 0 of 4, net zero rows):

    <span class="calendar-event-content__priority
                 calendar-event-content__priority--warm">warm</span>
    background: oklch(0.55 0.17 85 / 0.3)   color: oklch(0.8 0.15 85)

Verified in the BUILT css (dist/assets/index-BPmNuH4i.css), not just src —
built output now contains only --hot/--warm/--cold.

WHY IT SURVIVED 5 PRIOR UI AUDITS
  1. It is INVISIBLE to a screenshot or computed-style sweep, because the badge
     never renders today: all 4 tasks have due_date NULL, so /api/crm/calendar
     returns no task events, and activity events hard-code `priority: null`
     (crm.js:1100). It appears the moment any task gets a due date — i.e. normal
     app use.
  2. It is INVISIBLE to the Run 75/77 static className-vs-CSS set difference,
     which can only see literal class strings. An interpolated modifier is
     built at runtime, so neither side of that diff ever contained it.

ROOT CAUSE WORTH KEEPING: the low/medium/high/urgent vocabulary is real in this
app, but it belongs to AUTOMATION RULES (AutomationSettings.jsx:41-46), not to
tasks. The badge CSS was written against the automation priority list while the
data comes from the lead_priority enum. Same shape as Run 79's defect: a correct
idiom from one entity copied onto a different entity.

HOW IT WAS FOUND — new set difference, and it is EXHAUSTIVE
================================================================================
6th consecutive run where the finding came from a set difference over code.

    INTERPOLATED CSS MODIFIER CLASSES  vs  THE ENUM VALUES THAT CAN FLOW IN

Method: grep `[a-z][a-z0-9_-]*--\$\{[^}]+\}` across client/src, resolve each
interpolation to its data source (client constant -> API field -> DB column
type), then diff the reachable value set against the defined `.x--y` selectors.

The app contains EXACTLY FOUR such families, so this audit is closed, not
sampled — 1 of 4 was broken:

  1. calendar-event-content__priority--${priority}   BROKEN (above)          FIXED
  2. lead-table__priority-dot--${lead.priority}      hot/warm/cold: 3/3 defined  OK
  3. lead-table__stage--${lead.stage}                all 10 lead_stage enum
                                                     members defined           OK
  4. public-estimate-status--${estimate.status}      guarded by `isResolved`
                                                     to accepted|declined|
                                                     expired; 3/3 defined      OK

Note on #4: the estimates CHECK constraint allows 6 values (draft, sent, viewed,
accepted, declined, expired) and only 3 have CSS — but PublicEstimate.jsx:402
renders the badge only when `isResolved`, so the other 3 are unreachable. This
is correct; do not file it.

There are ZERO other dynamic class-construction mechanisms in the client: no
clsx, no classnames, no `className={map[key]}` lookups. Verified by grep.

NOTED FOR ANOTHER STAGE — NOT A UI ISSUE, NOT FIXED HERE
================================================================================
automationEngine.js:75-77 inserts into tasks:

    INSERT INTO tasks (tenant_id, lead_id, title, priority, due_date)
    VALUES (..., cfg.priority || 'medium', dueDate)

`tasks.priority` is the `lead_priority` enum (hot|warm|cold), so BOTH the
'medium' default and every value AutomationSettings.jsx offers (low/medium/
high/urgent) are invalid enum labels. Any automation rule that creates a task
should fail with 22P02 invalid input value for enum lead_priority.
This is a SERVER defect and outside the UI-audit charter — it is written up here
so the next api-test stage can reproduce it. It is also the origin of the CSS
vocabulary mismatch fixed above.
