THE DEFECT — /alerts storm-alert toggles rendered with no colour at all
--------------------------------------------------------------------------------
AlertSettings.jsx drove its two toggles ("Alerts Enabled", "Email Recipients")
through the third-party `react-switch` package, passing the app's oklch tokens:

    onColor="oklch(0.55 0.19 250)"   offColor="oklch(0.22 0.03 260)"
    onHandleColor="oklch(1 0 0)"     offHandleColor="oklch(1 0 0)"

react-switch does NOT hand those strings to CSS — it parses them itself so it can
interpolate the track colour during the flip animation. It cannot read oklch(), so
it emitted the track and handle with NO background property whatsoever:

    style="height:24px; width:44px; margin:0; position:relative;
           border-radius:12px; cursor:pointer; transition: background 0.25s;"
                                               ^^^ transitions a property never set

Measured: .react-switch-bg and .react-switch-handle both computed
backgroundColor = rgba(0, 0, 0, 0). Both toggles were completely invisible
against the glass panel, and ON was indistinguishable from OFF — on the only
screen that controls whether storm alerts are sent at all.

Screenshot evidence: .playwright-mcp/r78s3-toggle-crop.png (before — label
present, no control), r78s3-AFTER-on.png / r78s3-AFTER-off.png (after).

FIX: replaced with the toggle markup the app already uses in
SettingsView.jsx:1538 (Settings -> Storm Alerts — the duplicate of this very
panel) and OnboardingPage.jsx:729. Same 44x24 / 12px radius / 18px knob
geometry, --accent-green when on, role="switch" + aria-checked preserved from
react-switch's behaviour, plus an aria-label (the visible label is a sibling
element, so the control previously had no accessible name).

Verified after fix: ON  = oklch(0.75 0.18 155), knob translateX(20px)
                    OFF = oklch(0.3 0.02 260 / 0.6), knob translateX(0)
                    aria-checked flips true/false; 0 react-switch nodes remain.
The two duplicate storm-alert panels now render an identical control.
Toggled off and back on — stored config unchanged.

*** THE REUSABLE LESSON — WHICH THIRD-PARTY COMPONENTS BREAK ON oklch ***
--------------------------------------------------------------------------------
An oklch colour handed to a third-party component is only dangerous when that
component PARSES the colour to compute with it (interpolate, lighten, blend).
A component that passes the string through to CSS or an SVG attribute is fine —
the browser parses oklch natively.

  BREAKS   react-switch  — interpolates track colour across the flip animation
  FINE     recharts      — stroke="oklch(...)" goes straight to an SVG attribute
  FINE     Stripe Elements — style.base.color accepts oklch (mount-tested)
  FINE     mapbox/Google  — already fed hex (documented)

This distinction is the whole finding. I verified all three "FINE" cases rather
than assuming, and all three would otherwise have been filed as bugs.
